# 知识库条目质量治理工具

> 智能客服知识库"体检"工具：自动扫描 FAQ 条目，标记问题条目，生成可交付业务方的治理报告。

> **[📋 在线查看治理报告](https://3c3051b2b06549f4b17e0991cf1de926.bj8.agentos-app.net)** — 基于真实 40 条 FAQ 数据和业务规则摘要的检测结果

## 一、问题分类体系

基于知识库数据特征，定义 **8 类问题**，按严重程度分为三个等级：

| 问题类型 | 代码 | 严重等级 | 治理动作 | 说明 |
|---------|------|---------|---------|------|
| 条目矛盾 | `contradiction` | 🔴 严重 | 修改 | 不同条目对同一问题给出相互矛盾的回答 |
| 问答不匹配 | `qa_mismatch` | 🔴 严重 | 修改 | 回答内容与问题无关或答非所问 |
| 内容过时 | `outdated` | 🟡 重要 | 修改 | 引用已过期的活动、旧版政策、已下线功能 |
| 回答不完整 | `incomplete` | 🟡 重要 | 修改 | 回答未覆盖问题涉及的关键方面 |
| 信息模糊 | `vague` | 🟡 重要 | 修改 | 回答过于笼统，缺少具体数据或步骤 |
| 链接失效 | `dead_link` | 🟡 重要 | 修改 | 包含失效链接或内网/测试地址 |
| 内容重复 | `duplicate` | 🔵 一般 | 合并 | 问题表述不同但实际内容高度相似 |
| 格式不规范 | `format_issue` | 🔵 一般 | 修改 | 多余空行、不一致间距、混乱分隔符 |

### 各类问题的影响

- **条目矛盾**：用户收到矛盾信息后产生困惑，客服自动回复可能给出错误答案，直接损害信任
- **问答不匹配**：用户无法获得有效帮助，需二次咨询，增加客服压力
- **内容过时**：向用户提供过期信息，导致错误的操作指引
- **回答不完整**：用户无法获得完整解答，需二次咨询
- **信息模糊**：用户无法据此采取行动，降低知识库实用价值
- **链接失效**：用户点击后无法访问，导致信息断层
- **内容重复**：增加维护成本，更新时容易遗漏导致信息不一致
- **格式不规范**：影响阅读体验，在客服自动回复中显示异常

## 二、检测方法

### 2.1 双引擎 + 业务规则检测架构

工具采用 **业务规则检测 + 规则检测 + LLM 检测** 三层架构：

```
知识库数据 + 业务规则摘要
    │
    ├─────── 业务规则检测器 ────┐
    │  · 解析当前业务规则        │
    │  · 检测与规则冲突的答案    │
    │                            │
    ├─────── 规则检测引擎 ──────┤
    │  · 正则表达式匹配          │
    │  · 文本相似度计算          │
    │  · 启发式规则              │
    │  · 跨条目对比              │
    │                            │
    ├─────── LLM 检测引擎 ──────┤
    │  · 语义分析                │
    │  · 上下文理解              │
    │  · Mock 模式 / API 模式    │
    │                            │
    └─────── 结果合并去重 ──────┘
               │
          治理报告
```

### 2.2 业务规则检测（新增）

通过 `--context` 传入当前业务规则摘要（Markdown），工具会：

1. 识别规则中的关键事实（如"普通商品7天无理由退货"、"不支持货到付款"）
2. 将事实编码为可检测的规则（主题词 + 禁止词）
3. 对每个条目，若问题涉及该主题且答案包含禁止信息，则标记为 **内容过时/业务规则冲突**

当前已编码的关键规则包括：退货时间/运费、发货时效、合作快递、支付方式、发票类型、会员门槛、优惠券活动、客服时间等。

### 2.3 规则检测（Rule-based）

| 检测项 | 方法 | 说明 |
|-------|------|------|
| 内容过时 | 正则匹配 + 业务规则 | 匹配旧年份、已下线功能名，以及与当前业务规则冲突的答案 |
| 格式不规范 | 正则匹配 | 检测连续空行、不一致分隔符、混用括号样式等 |
| 信息模糊 | 启发式规则 | 答案过短(<15字)、匹配模糊表述模板 |
| 链接失效 | 正则匹配 | 检测内网IP(192.168/10./localhost)、测试域名、旧域名 |
| 问答不匹配 | 主题词检测 | 检测问题主题词在答案中缺失 |
| 回答不完整 | 启发式规则 | 多方面问题+短答案、操作类问题无步骤、空答案 |
| 内容重复 | 文本相似度 | SequenceMatcher 计算问答相似度；问题完全相同也判定重复 |
| 条目矛盾 | 跨条目对比 | 高度相似问题(q>0.85)但答案差异大；同题不同答重点标记 |

### 2.3 LLM 检测（Mock / API）

- **Mock 模式**（默认）：基于语义规则模拟 LLM 返回，无需 API 密钥，适合离线运行
- **API 模式**：支持 OpenAI 兼容 API，批量发送条目进行深度语义分析

LLM 检测补充规则检测的盲区，重点关注：
- 语义层面的问答不匹配（非关键词层面的）
- 信息模糊（缺少具体数据/步骤）
- 回答不完整（语义覆盖度）
- 内容过时（语义识别旧信息）

### 2.4 结果合并策略

同一条目同一问题类型，如果规则和 LLM 都检测到，标记为"双重确认"，提升可信度。

## 四、治理建议逻辑

### 4.1 治理动作

- **修改**：更新过时内容、修复格式、补充不完整回答、修正问答不匹配
- **合并**：将重复条目合并为一条，保留表述最清晰的版本
- **新增**：补充覆盖缺失的主题
- **删除**：对完全无价值的条目（如已被合并的重复条目）

### 4.2 优先级计算

优先级分数 = Σ(问题严重等级权重) + 多重问题加分 + 双重确认加分 + 模板加成

- 严重(critical) = 3分，重要(major) = 2分，一般(minor) = 1分
- 多重问题 +1分，双重确认 +1分
- 最终归一化到 1-10 分，映射为 P0/P1/P2/P3

### 4.3 长期治理建议

1. 建立定期巡检机制（每月运行检测工具）
2. 制定知识库编辑规范（统一格式、标点、链接标准）
3. 设置审核流程（新增/修改需审核后发布）
4. 活动类条目自动过期机制
5. 引入用户反馈机制（"有用/无用"反馈作为质量信号）
6. 定期补充覆盖（根据客服对话日志分析高频问题）

## 六、快速开始

### 6.1 环境要求

- Python 3.8+
- 无第三方依赖（纯标准库实现）

### 6.2 运行

```bash
# 运行检测（真实数据 + 业务规则，Mock 模式）
python main.py --input data/real_kb_articles.json --context data/business_context.md

# 运行检测（API 模式）
python main.py --input data/real_kb_articles.json --context data/business_context.md \
    --llm api --api-key YOUR_KEY --api-base https://api.openai.com/v1

# 仅输出 JSON
python main.py --input data/real_kb_articles.json --context data/business_context.md --format json
```

## 八、局限性说明

1. **中文分词**：使用字符级分词，未使用专业分词库，可能影响关键词重叠计算的精度
2. **重复检测**：基于文本相似度，无法识别语义相同但表述完全不同的重复
3. **矛盾检测**：仅检测数值差异和答案相似度，无法理解深层语义矛盾
4. **Mock 模式**：模拟 LLM 返回，精度低于真实 API 调用
5. **覆盖缺失**：基于预定义问题清单，无法自动发现未知缺失主题
